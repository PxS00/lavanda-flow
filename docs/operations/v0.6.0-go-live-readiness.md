# v0.6.0 go-live readiness

## Assessment

**NOT READY** for final v0.6.0 operator cutover.

The exact candidate passed all fresh automated, disposable runtime, persistence, security, inventory,
production, backup, restore, notebook, tablet, reboot, and current Windows-host resource checks recorded on
2026-09-10. The former physical-device, shortcut/browser lifecycle, reboot, idle-resource, and off-notebook
backup evidence gaps are resolved.

Release acceptance remains incomplete only where the supplied current-candidate evidence does not cover a
separate explicit path: real-Angular session-expiry handling, a representative CSRF-protected write from the
physical tablet on a safe boundary, sleep/closed-lid/Wi-Fi-disconnection availability behavior, current
Windows Firewall/router exposure state, and the complete maintainer runbook path. The earlier #186
physical-workstation record is not credited for those paths because an unchanged environmental assumption was
not recorded for this campaign.

The validation specification,
`docs/specs/0187-validate-v0.6.0-local-go-live-readiness.md`, was captured after the automated and isolated
acceptance evidence in this report had already been produced. It is not pre-execution evidence and does not
retroactively change the provenance of this run. Issue #187 was the executable source of truth during that
partial execution.

No production-code blocker was discovered, and no production code was changed.

- the persisted operator account remained usable after bootstrap configuration was removed;

- normal responses and Compose logs did not disclose the disposable database or operator credentials;
- PostgreSQL had no published host/LAN port.

- an insufficient-stock loss returned `422`, and a database check found zero negative balances;
- dashboard, expiration alerts, and immutable `ENTRY`/`CONSUMPTION` movement history remained coherent.

Production and traceability passed:

Persistence and local operation passed:

- closing the validation client did not stop either service;

- full Compose service restart preserved those records and returned health to `UP`;
- idle snapshot: application `0.11%` CPU and `627.9 MiB` RAM; PostgreSQL `0.02%` CPU and `41.7 MiB` RAM;
- no continuous abnormal idle CPU activity or unnecessary third long-running service was observed.

Recovery passed:

## Blockers and required follow-up

The prior notebook/tablet visual, shortcut/browser lifecycle, reboot, resource-observation, and off-notebook
backup blockers are resolved by the fresh evidence above. The following evidence blockers remain; none is a
production defect, so no focused product-fix issue is warranted from this validation record:

1. On the real Angular client, prove session-expiry handling returns the UI to authentication without protected
   data or stale successful state. Logout/login and restart-session behavior are not session expiry.
2. From the physical tablet, perform and record one representative authenticated CSRF/XSRF-protected write
   against an explicitly safe isolated/disposable boundary. Do not put synthetic data in the real operational
   database.
3. On the prepared host, record powered closed-lid, sleep, shutdown, and Wi-Fi-disconnection behavior against
   the documented local-first availability limitation.
4. Recheck and record the current Windows Firewall application-rule scope and router no-forwarding/no-public-
   exposure state without recording router identifiers or credentials. The unpublished PostgreSQL host port is
   already passed, but it is not proof of those two configuration states.
5. Execute the real-workstation maintainer runbook path for health/status/start/stop/restart/update/backup/
   restore and record that no undocumented critical step was required.

Per issue #187, these evidence gaps must be resolved before closing the acceptance gate. No product
implementation was added to this validation branch.

## Remaining risks

- Session expiry, a safe physical-tablet write, availability during sleep/closed-lid/Wi-Fi loss, firewall/router
  exposure, and the complete maintainer path remain unproven as listed above.
- Windows network configuration can drift after this observed reboot; the current topology proves no published
  PostgreSQL host port, but does not replace the remaining Firewall/router inspection.
- The release tag does not yet exist; the runbook's exact-tag checkout/update path still needs final cutover
  execution after acceptance.
- Restore was proven with synthetic representative data. The first real cutover still requires the documented
  immutable-source checksum, `DRY_RUN` before `APPLY`, empty-target guard, review, backup, and post-import
  verification steps.
- Recovery remains logical backup/restore rather than high availability, replication, or point-in-time
  recovery, as explicitly accepted for v0.6.0.
