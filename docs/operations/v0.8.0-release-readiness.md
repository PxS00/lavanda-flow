## Architecture and invariant evidence

`ModularityTest` passed. `sales` depends only on public `customers`, `catalog`, `inventory` and
`shared::error`; customers has no sales dependency, and inventory receives opaque audit references.
No cross-module persistence import or new module/dependency was introduced during preparation.

- Sales application services own transactions and lock the order before lifecycle/correction work.
  Inventory sale withdrawal/return contracts require that caller transaction (`MANDATORY`).
- Inventory owns FEFO, current item/category/unit eligibility, expiration, item-before-batch locking,
  balances and immutable movements. Quantity arithmetic is BigDecimal/NUMERIC(19,6); nonnegative
  stock remains protected in domain and database. `expiresAt <= today` is expired using application Clock.
- Confirmation commits every withdrawal, movement, snapshot, allocation and final state atomically.
  Confirmed retries return stored history without live lookup or another stock call. Concurrent
  confirmation, insufficient later-line stock and injected persistence/lock failure are regression-tested.
- Corrections leave the original sale/lines/allocations untouched, sum previous accepted returns under
  the sale lock and enforce the original line/batch limit. Identical sale-scoped IDs return stored
  audit even after expiry; changed payload conflicts. Concurrent retries/distinct IDs, rollback after
  inventory effects, depleted eligible batches and rejection of expired/undated/ineligible stock pass.
- PostgreSQL immutable-history triggers and duplicate-consumption defenses remain enabled and tested.
  Auth, authorization, CSRF, exact HTTP values and pt-BR workflow regression suites remain enabled.

## Flyway V1–V20 and compatibility

The complete SQL chain was inspected and compared byte-for-byte: **V1–V16 equal production** and
**V1–V20 equal the fixed integrated base**. There are exactly 20 sequential versioned SQL files.
No historical migration, checksum, trigger or data was rewritten during preparation.

V1–V16 retain the baseline/framework registry, catalog/suppliers, exact batch/movement quantities and
constraints/indexes, minimum stock, production metadata/formulas/lot allocation/immutable genealogy,
operator accounts, finished products and packaged filling. New commercial schema is:

| Migration | Change and proof |
| --- | --- |
| V17 | Customer contacts, bounds/checks and active/name/ID index; V16 upgrade retains supplier rows and supports old/new writers |
| V18 | Orders/lines, nullable customer FK, exact quantities/prices/amounts and paging indexes; V17 upgrade preserves contacts and draft writers |
| V19 | Nullable opaque movement references, confirmation snapshots, immutable triggers and sale allocations/FKs; V18 upgrade preserves movement, batch, draft and production genealogy data |
| V20 | Immutable correction audit with sale-scoped PK, association/allocation FKs, unique movement and positive/true-only checks; V19 upgrade preserves historical sale/line/allocation/movement/batch rows |

V20 creates the replacement uniqueness index **before** dropping the V19 broad index, inside the
Flyway PostgreSQL transaction. The replacement keeps the same referenced source/line/batch uniqueness
for all non-ADJUSTMENT_IN movements. Duplicate CONSUMPTION still fails; multiple legitimate positive
partial returns succeed. Migration retry is a no-op and validation passes in dedicated upgrade tests.

Clean PostgreSQL 17.11 Testcontainers migrations and V14/V16/V17/V18/V19 upgrade tests passed.
Separately, the clean image started with the actual `operational` profile (`ddl-auto: validate`) against
a fresh disposable PostgreSQL: Flyway history reported **20 versioned migrations, latest 20, zero
failures**, Hibernate initialized successfully, and `/actuator/health` returned UP.

Forward rollout applies V17–V20/backend before the matching UI; old inventory writers omit nullable
references and retain compatible columns. New confirmation/history/correction traffic requires the new
backend. Rollback retains expanded schema and all committed sale/return audit, loses newer UI/API
capabilities and does not undo stock effects. Old-binary Flyway/schema compatibility must be checked
before an application rollback; it was not established by running v0.7.1 against V20. Never recreate
V19's broad index after returns exist. No destructive down migration or automatic downgrade is safe.
V20 index creation can lock/scan stock movements; production-volume timing was not measured.
